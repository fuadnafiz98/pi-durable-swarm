@earendil-works/pi-durable runs AI agents as committed state: every input, every streamed partial, every tool call lands in a storage transaction before anything reads it. A crash costs you a process, never the conversation. This page walks one session end to end — from hub.submit() to a durable answer — then adds choreography (tasks, swarms, restarts) and the places the same code can run: a laptop, a Durable Object cell, a fleet.

Everything drawn here was read in the pi-mono package sources (the checkout sits beside this lab; receipts point into pi/packages/…) and run in a lab of experiments (the swarm patterns, the real SIGKILL, the factory blueprint). Because the figures follow the source, they carry file-and-line receipts; hover anything.

TL;DR for builders: one session = one storage file; one commit = the unit of durability; the scheduler is a paused pump that waits and aborts turn on; ownership decides what aborts and waits reach — those four ideas explain every figure below.

02 · WORKFLOWWhat happens to one input?

Nothing about a round is memory-only. The input arrives, the scheduler groups it into a run, the model streams through a durable task, and the answer is appended like everything else. Step through the round.

03 · STORAGEWhat makes a commit the unit of durability?

Not a save — a transaction. You read committed state plus your drafts, decide, and the returned value becomes the thing that survives. Step through what physically happens on every commit.

04 · SUBMISSIONSWhat exactly am I waiting on?

A submission is the durable handshake between you and a session: queued → placed → done (or unanswered). It lives in a table, so the wait itself survives restarts. Pick the kind.

05 · STATEWhere does work stop and start?

Every unit of work — a generation, a tool call, a compaction, one of your tasks — is the same durable record with the same five states. The invocation is the only part a restart loses. Pick a state to see what holds it.

07 · STRUCTUREWhat holds what up?

Four layers rest on one swappable storage contract. Your extension code sits at the top; the built-ins are extensions too. Below, the SQLite layer keeps nine public tables — the very names a Durable Object cell keeps.

08 · TIMEWhat does a crash actually cost?

Two rounds in the life of one conversation. In the second, the process dies mid-stream under SIGKILL and another process opens the same storage. Watch what the timeline keeps: the committed partial, the demotion, the retry.

verified on this machine · experiment 05

The SIGKILL landed with 144 streamed chars unflushed. The second process reopened storage, demoted the run, called resume(), and the answer still committed: 2 550 chars across five entries — visibly different words from the first attempt. A retry, not a replay.

09 · PUMPWhat turns work on?

Commits alone never start work. The scheduler is a pump that ships paused, and only four kinds of calls flip the switch — including one explicit kick.

10 · CALL STACKWho runs one submit?

The same round as a stack of frames. Note what happens as it unwinds: frames vanish, state stays — every step the stack took was already a commit.

11 · SWARMHow do many agents hold still?

Ownership is pi-durable's choreography: a task that owns a thing decides what its aborts and idle waits reach. Three patterns cover most swarms — and one of them has room for a foreign agent joined through a real CLI.
